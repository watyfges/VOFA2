# 远程调参（移动端）设计与实现说明

本文是「VOFA2 远程调参」功能的方案说明，先给结论，再给协议细节。PC 端已按本文实现，
移动端可以照本文直接对接。

---

## 1. 需求拆解

| 编号 | 需求 | 落点 |
| --- | --- | --- |
| R1 | PC 打开选项后成为局域网服务端 | `AppController` + `RemoteControlServer` |
| R2 | 手机通过局域网连接，控制右侧调参栏 | WebSocket 控制通道 |
| R3 | 只控制**已有**控件：数值输入、开关、滑条、一键发送 | 复用 `commandStore_` / `actions_`，不新增命令语义 |
| R4 | PC ↔ 手机、手机 ↔ 手机实时双向同步 | 服务端权威 + 增量广播 |
| R5 | PC 显示当前连接客户端数量 | 工具栏常驻计数 + 对话框客户端列表 |
| R6 | 手机启动后自动搜索服务端，显示 IP 与名称 | UDP 广播发现（端口 47901） |
| R7 | 支持多客户端同时连接 | 连接表 + 广播，上限 16 |

明确不做的事：手机端不能新增/修改/删除命令、绑定、命令组，不能改协议与串口参数，
不能发任意原始字节。手机的所有写操作都会被翻译成 PC 现有按钮会触发的同一个函数调用，
因此单片机收到的字节与 PC 操作完全一致。

## 2. 通信方式

**控制通道：WebSocket（RFC 6455，文本帧 + JSON）**，默认 TCP 47900。

选择理由：

1. 手机端可以是原生 App，也可以直接是浏览器页面（同一端口另提供 `GET /` 的探活响应），
   不必为 iOS/Android 各写一套 TCP 客户端。
2. 有明确的消息边界，天然适合 JSON 增量同步，不用自己做粘包处理。
3. 自带 ping/pong 心跳，手机切后台、Wi-Fi 漫游后能快速发现掉线。

本机 Qt 6.8.3 未安装 `Qt6::WebSockets` 模块，因此 `src/remote/WebSocketServer.*` 实现了一个
**服务端子集**：握手校验、文本帧、分片、ping/pong、close。约 300 行，已被单元测试覆盖。

**发现通道：UDP 广播**，固定端口 47901。客户端向 `255.255.255.255:47901` 广播探测包，
服务端单播回复名称、控制端口、协议版本、是否需要访问码、本机 IPv4 列表。
手机端拿到回复后按「回复来源 IP」连控制端口，即使用多网卡也不会连错。

端口冲突时用户可在 PC 端改控制端口；发现端口固定（手机端需要它才能自动发现）。

## 3. 消息格式

统一信封：一个 WebSocket 文本帧 = 一个 JSON 对象，`t` 字段区分类型，上限 64 KiB。

### 客户端 → 服务端

```json
{"t":"hello","proto":1,"clientId":"pixel-8f2a","name":"Pixel 7","pin":"1234"}
{"t":"value","id":1000,"v":12.5}
{"t":"commit","id":1000,"v":12.5,"exact":false}
{"t":"action","id":3,"trigger":true}
{"t":"action","id":3,"on":true}
{"t":"oneclick","group":"底盘/PID","intervalMs":100}
{"t":"oneclick.stop"}
{"t":"sync"}
{"t":"ping"}
```

- `value`：拖动中的实时值，走 PC 现有的 33 ms 限流，只影响「拖动时实时发送」开关允许的发送。
- `commit`：松手/输入完成的最终值，**一定**下发一次。`exact:true` 表示数值输入框提交，
  允许超出滑条 min/max（与 PC 的数值输入框行为一致）。
- `action`：`kind=0` 按钮用 `trigger`；`kind=1` 开关用 `on` 指定目标状态（幂等，不翻转）。
- `oneclick`：只发当前组内被勾选、且属于该组的滑块，顺序与 PC 一致。

### 服务端 → 客户端

```json
{"t":"welcome","proto":1,"session":3,"name":"调试台","version":"0.1.0","pin":false,"maxClients":16}
{"t":"state","seq":12,"server":"调试台","groups":["默认","底盘/PID"],
 "controls":[{"id":1000,"label":"kp","group":"默认","v":1.5,"min":0,"max":10,"step":0.01,"inc":true}],
 "actions":[{"id":3,"label":"启动","group":"默认","kind":0,"on":false}],
 "pcGroup":"默认","conn":{"connected":true,"state":"已连接"},
 "oneclick":{"sending":false,"sent":0,"total":0,"status":"","interval":100}}
{"t":"value","id":1000,"v":1.6,"from":"pc"}
{"t":"action","id":3,"kind":1,"on":true,"from":"c3"}
{"t":"oneclick","phase":"step","sent":2,"total":5,"status":"已发送 2/5: kp"}
{"t":"conn","connected":true,"state":"已连接"}
{"t":"clients","count":2}
{"t":"error","code":"unknown_control","message":"绑定不存在"}
{"t":"pong"}
```

`state` 是**全量快照**，手机收到即整体替换本地模型，不做差分合并——简单且不会错位。
`seq` 单调递增，客户端发现跳号就发 `sync` 重新拉快照。

## 4. 同步机制

**服务端权威 + 增量广播 + 全量纠正。**

1. 唯一真相源是 `AppController` 内的 `commandStore_`（滑块）和 `actions_`（按钮/开关）。
   PC 与手机都只是它的视图。
2. 任何一次写入（无论来自 PC 还是手机）都在 Qt 主线程串行执行，执行完把**结果**广播给
   **所有**客户端，包括发起者。发起者收到自己的回声即代表写入已被服务端确认。
3. 值变更走 `value` 增量，33 ms 合并一次（`QHash<bindingId, value>` + 定时器），
   避免多台手机同时拖动时刷屏。
4. 结构性变化（增删滑块、增删命令、切换/增删命令组、改模板）走全量 `state`，
   80 ms 防抖，保证客户端不会出现「控件对不上号」。
5. 冲突策略：**最后写入者获胜（LWW）**。两个手机同时拖同一个滑块时，后到的一次生效，
   回声会把所有人拉到同一数值。这是调参场景下最符合直觉的策略，不需要锁和令牌。
6. 手机端的「命令组」是**本地视图状态**：快照里带全部组和全部控件，由手机自己筛选，
   不改变 PC 当前组。只有在点「一键发送」时才把组名显式发给服务端。
7. 一键发送是全局互斥的：正在发送时服务端拒绝新的 `oneclick`，返回 `busy`，
   但会把 `oneclick` 进度持续广播给所有客户端。

## 5. 界面划分

**PC 端（本次实现）**

- 顶部工具栏新增「远程调参」按钮，旁边常驻状态文字：未启用 / 等待手机连接 / `N 台手机在线`。
- 对话框「远程调参（手机局域网）」：
  - 启用开关、本机名称、端口、访问码（留空表示不校验）
  - 状态行（运行中 / 错误原因）
  - 手机连接地址列表（`ws://192.168.x.x:47900`，可直接复制）
  - 在线客户端：名称、IP、连接时间，可单独断开
- 右侧调参栏本身不做改动：手机操作的正是这些控件，PC 界面上会实时看到数值/开关变化
  （因为手机写入走的是与 PC 相同的函数，`oneClickBindings_` 与 `actionBindings_` 会刷新）。

**手机端（下一步实现）**

- 启动 → UDP 广播发现 → 列出「服务端名称 + IP:端口」→ 点击连接
- 连接后：命令组下拉、滑块 + 数值输入框、开关、按钮、一键发送（带进度）、连接状态
- 只读展示 PC 的串口/TCP 连接状态，方便判断板子是否在线

## 6. 安全与限制

- 仅监听局域网可达端口，不做公网穿透。
- 访问码可选：设置后 `hello` 必须带正确 `pin`，否则返回 `bad_pin` 并断开。
  实验室共用 Wi-Fi 建议开启。
- 客户端数量上限 16，单条消息上限 64 KiB，未带掩码的帧直接断开（RFC 要求）。
- 心跳 15 s，45 s 无任何数据判为掉线并清理。
- 所有远程写入都做存在性校验：控件 id 必须存在于当前命令表，数值必须有限。

## 8. 已经验证过的行为

`ctest` 全部通过（含 `vofa_remote_tests` 10 项）。另外用一个不依赖 Qt 的
Python 客户端（`scripts/remote_ws_probe.py`）独立验证了：

- 握手、`welcome` + `state` 快照下发；
- 手机写入后 PC 模型立即变化，并把 `value` 回声带 `from=cN` 广播回来；
- PC 侧修改滑块后手机会收到 `from=pc` 的增量；
- 两台手机同时在线时，PC 工具栏显示「2 台在线」，列表逐条列出名称、IP、连接时间。

启动参数（调试用）：

```bat
vofa2_app.exe --remote                 # 启动即开启远程服务（默认端口 47900）
vofa2_app.exe --remote-port 48000      # 指定端口
vofa2_app.exe --open-dialog remote     # 启动即打开远程调参对话框
```

## 9. 稳健性：半包、乱码与洪水的处理

设计目标不是「抵御公网攻击」，而是**任何手机端异常都不能影响 PC 的调参与会话**：
断网、半包、乱码、疯狂重连、发一堆随手拼的 JSON，最坏结果只能是「这个连接被断开」。

### 硬性上限（都在 `RemoteProtocol.h`）

| 项 | 值 | 理由 |
| --- | --- | --- |
| 单条消息 | 64 KiB | 快照最大也就几 KB，超出直接关 1009 |
| 同时连接 | 16 | 手机调参用不到更多 |
| 同一 IP 连接 | 4 | 一台失控设备不能把 16 席全占了，把手机挡在门外 |
| 报文速率 | 300 条/秒，突发 160，按大小计费（1 + 每 KiB 1 点） | 拖动约 30 条/秒，留足余量；64 KB 垃圾只能发 2 条就被断开 |
| `hello` 超时 | 5 s | 连上不说话的直接清掉 |
| 心跳 | 15 s ping，45 s 无数据判定掉线 | 手机切后台、Wi-Fi 漫游能及时发现 |
| 发送积压 | 512 KiB | 手机不读数据时主动断开，不让服务端无限缓冲 |
| 每轮 accept / 发现回复 | 32 个 / 200 次每秒 | 连接风暴、探测洪水都不许霸占 UI 线程 |

协议层一律「先校验再分配」：未加掩码的帧、非法 opcode、超长帧头、分片状态错误，
都是立即关闭连接，不进入 JSON 解析。JSON 解析失败只回一条 `error`，连接继续可用。

### 压测中发现并修掉的问题

1. **心跳/广播时可能迭代器失效**：`close()` 可能同步触发 `disconnected`，从客户端表里删元素，
   而当时正用 range-for 遍历同一个 vector —— 属于未定义行为，极端情况下会崩。
   现在先收集 session 再逐个操作。
2. **`intervalMs` 的 double → int 转换**：JSON 里塞 `1e12` 时 `static_cast<int>` 是未定义行为，
   改为先 `clamp` 再转换。
3. **不读数据的客户端**：发送缓冲会无限增长，长时间运行可能吃光内存。
   现在超过 512 KiB 就断开（1011）。
4. **每次连接都写日志 + 重建 QML 列表**：连接风暴下 UI 线程被 I/O 拖慢（实测 p50 从 4 ms 涨到 400 ms）。
   日志限频到 4 条/秒，客户端列表 120 ms 合并刷新。
5. **单设备占满连接数**：增加单 IP 4 席限制。

### 验证方式

- `ctest` 中的 `vofa_remote_robustness_tests`（18 项）覆盖：握手前垃圾、超长/半截握手、
  无掩码帧、伪造 1 TiB 帧长、超长消息、逐字节半包、分片重组、坏 JSON（截断/非对象/非法 UTF-8/
  万层嵌套/未知类型）、ping/close 控制帧、洪水限流、慢读客户端、120 次快速重连、
  40 轮随机模糊流量、同址占位，以及控制器层的恶意写入（`1e999`、不存在的 id、越权类型）。
- `scripts/remote_stress.py`：对**正在运行的** app 做多线程攻击，跑完再验证
  「握手 → 快照 → 写值 → 回声」是否仍然正常，并采样进程 RSS。

实测（Windows 11 / Release 构建）：

| 场景 | 结果 |
| --- | --- |
| harsh：10 个攻击线程 25 s | 18 690 次连接、280 940 帧、167 MB 垃圾；进程存活，RSS 260→251 MB，攻击结束后立刻可用 |
| normal：1 台设备边调边捣乱 20 s | 77 次手机连接 66 次成功，p50 **4 ms**、max 43 ms，RSS 基本不变 |

harsh 档里手机连接成功率低，是因为攻击者与「手机」在测试中同为 127.0.0.1，共享那 4 个席位；
真实局域网里手机有自己的 IP，不会和捣乱设备抢同一份额度。
